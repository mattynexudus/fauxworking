# Nexudus Test Data — Agent Instructions

## What this repo does

Generates and seeds realistic test data into a Nexudus instance via MCP tools.
The data populates all reports and dashboards defined in the reports repo.

## Key commands

- `python generators/00_reference.py` — Tax rates, financial accounts, resource types
- `python generators/01_structural.py` — Tariffs, products, resources, desks, inventory, discounts, CRM boards
- `python generators/02_people.py` — Coworkers (with engagement fields) and visitors
- `python generators/03_contracts.py` — Contracts (with ContractTerm), deposits, freezes, occupancy
- `python generators/04_activity.py` — Bookings (recurring + products + guests), check-ins, credits, passes
- `python generators/05_community.py` — Deliveries, events, help desk, threads, blogs, tasks
- `python generators/06_financial.py` — Trigger invoices, pay/void/credit, ledger supplements
- `python generators/07_crm_proposals.py` — Opportunities, proposals (accept some → auto contracts)
- `python generators/daily_update.py` — Create today's check-ins, bookings, visitors, deliveries
- `python teardown.py` — Delete every tracked record (agent-run; see rule 6)
- `bash scripts/seed_all.sh` — Run all generators in order
- `bash scripts/daily.sh` — Run daily update (fresh records for today)
- `bash scripts/verify.sh` — Count tracked records against config.py targets
- `bash scripts/teardown.sh` — Confirmation prompt + dry-run preview; live deletion needs an agent (see `teardown.py`)

## Standing rules

1. **All dates are rolling** — derived from `config.TODAY`. Never hardcode dates.
2. **Check idempotency** — before creating, query for existing records with same key.
3. **Respect dependency order** — never create a child before its parent.
4. **Use config.py** for all magic numbers (volumes, dates, business IDs).
5. **Dates must be UTC with Z suffix** — use `config.to_utc_str()`.
6. **Never delete production data** — teardown only deletes IDs logged in `data/created-ids/<entity>.json`, never by name pattern. Note: entities only mutable via commands (e.g. `coworkerinvoices` void/credit-note records — see rule 12) have no plain delete path other than `COWORKER_INVOICE_DELETE`, which `teardown.py` does not currently special-case; it may error or no-op on these tracked entries. Not yet exercised live.
7. **No `[TEST]` name prefixes** — records should look like real data (reports/dashboards are demoed off this). `TEST_NAME_PREFIX` in `config.py` is `""`. The only marker baked into a record is the coworker email (`test-{id}@seeddata.local`); everything else is identified purely by its tracked ID.
8. **No "whoami" MCP tool** — resolve business/currency/country/timezone via `nexudus_list("businesses", {})`, and the admin user (for `IssuedById`/`ResponsibleId`) via `nexudus_list("users", {})` filtered to `IsAdmin=true`. A login can have access to more than one business — `pipeline._select_business()` never silently picks one; it auto-selects only when there's exactly one, otherwise requires an explicit `business_id` (via `--business-id` on any generator/`pipeline.py`, or `wizard.py`'s interactive prompt) and fails loudly listing the options if that's missing or wrong.
9. **Log all created IDs** — append to `data/created-ids/<generator>.json` (one file per generator, not per Nexudus entity — each record is tagged with an `"entity"` field; see `teardown.py`).
10. **One MCP call at a time** — do not parallelise Nexudus calls.
11. **Cancelled bookings** — create the booking, then cancel it via `nexudus_run_command("bookings", "CANCEL_BOOKING", [id], parameters=[{"Name": "Cancellation Reason", "Value": <eBookingCancellationReason>}, {"Name": "Cancel without applying cancellation fee rules", "Value": true}])`. Confirmed live: a raw delete leaves `CancellationReason` at 0/Unknown. Reason enum values in use: NoLongerNeeded=1, TooExpensive=2, RebookedForADifferentTime=4, FailedToPayUpfront=5, NotCheckedIn=8 (see `CANCELLATION_REASON_MAP` in `generators/04_activity.py`).
12. **Invoices** — cannot be created directly; raise via `nexudus_run_command("coworkers", "COWORKER_BILL_RUN", [coworkerId, ...])`, which bills that coworker's active contract(s) plus any pending item sales (see rule 26). `coworkerinvoices` *does* support commands — confirmed live, despite not appearing under command discovery (see rule 27):
    - `VOID_INVOICE` (no parameters) — sets `Void=true` on the same record.
    - `COWORKER_INVOICE_CANCEL` (parameters: an `"Amount{invoiceId}"`-named field — the invoice ID is baked into the parameter *name*, not a separate value — plus `Preview` and `DoNotApplyCreditAutomatically`) — creates a *new*, separate negative-amount invoice with `CreditNote=true`, linked back via `OriginalInvoiceGuid`. This is credit-noting, not voiding.
    - `COWORKER_INVOICE_DELETE` — genuinely deletes the invoice (404 on follow-up GET). Not equivalent to void — it erases the audit trail. Don't use it for void/credit-note scenarios.
    - `COWORKER_INVOICE_REFUND` (parameters: `Amount{invoiceId}`, `Preview`, `ePaymentProvider0`) — only valid on an already-paid invoice. Unlike credit-note, flips `Refunded=true` + `RefundedOn` on the *same* record rather than creating a new one — confirmed live. `RefundedAmount` stays `0` despite existing on the schema, also confirmed live, unexplained. The `nexudus_run_command` MCP tool itself refuses this entity ("does not support run-command") even though the real API accepts it fine — verified working through this project's own direct REST client instead; this is the same false-negative pattern as command discovery (rule 27), just enforced client-side this time.
    Booking charges use `nexudus_run_command("bookings", "CHARGE_BOOKING", [bookingId])`, which sets `Booking.Invoiced=true` and creates the linked charge — not a standalone `CoworkerExtraService` with a manually-set `BookingId`.
13. **Proposals** — create at status=1 (Draft). Accepting requires commands, not a direct field update: `nexudus_run_command("proposals", "PROPOSAL_SEND", [id])` then `nexudus_run_command("proposals", "PROPOSAL_ACCEPT", [id])`. Confirmed live: a direct `ProposalStatus` update to 3 fails with "Accepted proposals cannot be changed," even on a brand-new Draft. Neither command appears under command discovery (see rule 27).
14. **Financial accounts** — assign to Products, ExtraServices, and Tariffs at creation time.
15. **Tax rates** — assign to Products, ExtraServices, and Tariffs at creation time.
16. **Discount codes** — apply via Proposal.DiscountCodeId or Booking.DiscountCode text field.
17. **Recurring bookings** — `Repeats` is schema-required even for one-offs (send `1`/Daily with `RepeatEvent=false`); set `RepeatEvent=true` + `RepeatEvery` + `RepeatUntil` for real series. `CalendarEvent` uses a different, more granular enum (`eCalendarEventRepeatCycle`) than `Booking`'s — don't assume they match.
18. **Booking products** — `BookingProducts` is a genuine inline child on `Booking.create` (`[{ProductId, Quantity}]`) — no separate call needed.
19. **Booking guests** — create `BookingVisitor` standalone with a real `VisitorId`, not via Booking's inline `BookingVisitors` (that path writes `VisitorFullName`/`VisitorEmail`, which are read-only on the standalone entity — ambiguous whether/how it resolves a Visitor).
20. **Daily update** — run `daily_update.py` for fresh daily records. Unlike the layer generators, it resolves its own context live (no `prev_output` chain) since it's meant to run standalone, repeatedly, long after the one-time seed.
21. **Events** — `CalendarEvent` has no inline children. Create order is `CalendarEvent` → `EventProduct` (a ticket type is **required** before any attendee, not optional) → `EventAttendee`. `OnlyForMembers` events reject `EventAttendee` creation for a coworker whose membership isn't *currently* active — contract cancelled, or in a currently-paused freeze (`CoworkerContract.InPausedPeriod`) — with `"You cannot purchase this product"`, confirmed live. This is enforced against the coworker's actual contract state, not the `Coworker.CanPurchaseEvents` flag (which stays `true` regardless). When generating attendees for such events, only pick from coworkers with a currently-active, unfrozen contract.
22. **Deliveries** — create as pending, then update `Collected=true` + `CollectedOn` (or `Forwarded`/`Recycled`/`ReturnedToSender` + their `*On` field) to mark an outcome.
23. **Community threads/messages** — require `UserId`, a field distinct from `CoworkerId`. Seeded coworkers have no linked User account (`Coworker.UserId` is `updateOnly`, not populated by creation), so the resolved admin user's ID is used as `UserId` throughout, with `CoworkerId` set alongside for attribution.
24. **Engagement fields** — `ChurnProbability`/`EngagementLevel` on `Coworker` are confirmed live: visible on GET, round-trip correctly.
25. **ContractTerm** — set on ~30% of contracts. This is the minimum term end date (start + N months), not a duration field.
26. **Item-sale invoicing** — `Booking`, `CoworkerExtraService`, and `CoworkerProduct` all support `InvoiceThisCoworker` (bill this person, not their team's payer). Set it `True` on all of them so their charges get swept into that coworker's next invoice by `COWORKER_BILL_RUN`, alongside their plan fee — this is the "item sales" invoicing path referenced in the original design, distinct from contract renewal itself.
27. **Command discovery is unreliable** — `nexudus_list_commands` and `GET .../commands?id=X` have both produced false negatives, confirmed live: missing `VOID_INVOICE` for `coworkerinvoices`, missing all of `proposals`' commands. If an entity's obvious field-update path fails with a vague error (e.g. "cannot be changed"), don't conclude the action is unsupported — check whether the entity has a `runcommand` endpoint, and if discovery doesn't surface what's needed, capture the real admin UI's network request instead. The `nexudus_run_command` MCP tool itself can carry the same false negative one step further and outright refuse a call ("does not support run-command") for an entity/command the real API accepts — confirmed live for `coworkerinvoices`/`COWORKER_INVOICE_REFUND`. When that happens, the generators' own direct REST client (not this MCP tool) is the one to trust — it's what actually runs live (see `nexudus_client.py`).
28. **Coworker has no `BusinessId` field** — it's two separate fields instead: `Businesses` (plural, a list — which businesses this coworker is linked to) and `InvoicingBusinessId` (their actual "home" business). Confirmed live: omitting both doesn't error, it silently falls back to some other business tied to the login/token; confirmed separately that updating `Businesses` alone does **not** move `InvoicingBusinessId` — both must be set explicitly. This only surfaces as a bug on a login with access to more than one business (see rule 8) — with a single-business account there's nothing for it to silently fall back to *other than* the right one, so this went unnoticed until tested against a multi-business login.
29. **Any `X_id = some_dict.get(...)` lookup on a possibly-skipped parent record needs an explicit `is None` guard before use** — a missing guard doesn't fail cleanly, it sends `null` for that field and the API rejects it with a misleading message (e.g. `BookingVisitor` with a skipped `Booking` fails as `"Booking: is a required field"`, not `"BookingId: null"`). This pattern is used correctly almost everywhere in the generators (see the many `if x_id is None: continue` guards) — `04_activity.py::_create_booking_guests` and `06_financial.py::_create_ledger_supplements` were the two places it was missing, both fixed. Audit new `.get()`-based parent lookups the same way, especially anything downstream of `Coworker` (the one record type most likely to be skipped, via the seat-limit `Exception` path in `02_people.py`).
30. **There's a ~50 coworker-creation limit per day, per the Nexudus API** (per-account, not per-business) — user-reported, not independently re-derived, but it matches the `"Access Denied"` behavior `02_people.py`'s existing seat-limit handling was already written defensively against. It resets some time later (exact window unconfirmed) — if a live run stops partway through coworkers with `"Access Denied"`, that's very likely this, not a bug, and every later layer's shortfall (bookings, contracts, etc. tied to the missing coworkers) cascades from the same root cause. Retrying immediately won't help; retrying tomorrow should.
31. **`nexudus_delete()` must check the response body, not just HTTP status** — confirmed live: a DELETE can return HTTP 200 (so `resp.ok` is `True`) with `WasSuccessful: false` in the body for a genuinely failed delete (e.g. a `BookingVisitor` its sibling record blocks from being deleted). `nexudus_client.py::nexudus_delete()` only checked `resp.ok` for a long time, which silently reported these as successes — the same class of bug `_unwrap()` already guards against for create/update/run_command, just missed on delete. Now fixed to check `WasSuccessful` the same way. If a delete-based fix ever looks like it "succeeded" but the record is still there on the next GET, suspect this pattern, not a timing issue.
32. **A `Visitor` who is a guest on more than one `Booking` can leave a `BookingVisitor` link permanently stuck** — confirmed live: cancelling a booking normally cascades-deletes its `BookingVisitor`(s) fine via `CANCEL_BOOKING`, and even a direct isolated `DELETE` on a normal `BookingVisitor` works. But when the same `Visitor` is attached to two different bookings, one of those two links can become permanently undeletable — every direct `DELETE` attempt on it fails identically and reproducibly with `"You must delete all booking visitors using this record before you can delete it."`, even in total isolation (not a timing/order artifact). The fix is not to pre-delete guests before cancelling (that doesn't work and isn't needed for the normal case) — `04_activity.py::_cancel_bookings` catches this specific error message and skips that one booking's cancellation with a warning, rather than crashing the whole run.
33. **An "open" `CheckIn` (no `ToTime` — still checked in) must be dated today** — confirmed live: a `CheckIn` with `Open=true` and `FromTime` on any day other than today fails with a generic, unhelpful 400 (`"Ooops! There was a problem while running this action..."`), not a field-specific message. Traced to a specific failing record (`FromDayOffset=-1`) to confirm. `prebuild.py::generate_checkins()` now forces `FromDayOffset=0` for the handful of check-ins it marks `Open`, rather than sampling from a "within the last few days" pool. `04_activity.py::_create_checkins` also now catches any create failure (not just the already-handled "no valid time pass" case) and skips that one record with a warning instead of raising — a bad check-in shouldn't take down the rest of the layer (extra services, credits, time passes, coworker products all run after it).
34. **`EventAttendee` effectively requires a real `CoworkerId`, despite the docs listing it as optional** — confirmed live via isolated testing: an ad-hoc "guest" attendee (just `FullName`/`Email`, no `CoworkerId` — the documented flow for non-member walk-ins) fails with a generic 500 (`"Ooops! There was a problem while running this action..."`), on every event tested, with `CheckedIn` either `true` or `false`, and even when a real `VisitorId` is substituted in instead of a guest name/email. Only ever succeeds with a real `CoworkerId` attached. Same "docs unreliable" pattern as rule 27, just for a field instead of a command this time. `prebuild.py::generate_event_attendees()` no longer generates ad-hoc guest attendees at all — every attendee now gets a real `CoworkerIndex` (still respecting rule 21's active-members-only restriction for `OnlyForMembers` events). `05_community.py::_create_event_attendees` also now catches any create failure and skips that one record with a warning instead of raising.
35. **`COWORKER_BILL_RUN` over a large batch is slow enough to risk a timeout or the generic 400** — confirmed live: a single call billing 42 coworkers at once took 28.8s (once genuinely exceeded the client's 30s timeout), right at the edge of producing an unhelpful failure with no way to tell which coworker (if any) was actually the problem. Testing each of the 42 coworkers individually (including several with a currently-frozen contract, to rule out rule 21's "frozen membership" pattern applying here too) all succeeded fine on their own — it's genuinely a batch-size/latency issue, not a bad record. `06_financial.py::_raise_invoices` now calls `COWORKER_BILL_RUN` in chunks of `BILL_RUN_CHUNK_SIZE = 10`, and a failed chunk is logged and skipped rather than aborting billing for every other coworker.
36. **`COWORKER_INVOICE_REFUND` rejects an invoice that includes a Deposit line** — confirmed live: `"You cannot refund X for line Deposit (#id)"`. `ContractDeposit` has its own refund path (`Refundable` + `Credited`, triggered by cancelling the parent contract), not a generic invoice refund — and `InvoiceLines` isn't populated on either the list or single-GET `coworkerinvoices` response, so there's no cheap way to detect this up front and exclude such invoices from the refund pool. `06_financial.py::_refund_invoices` now takes the full refund-candidate pool (not pre-sliced to `REFUND_COUNT`) and falls through to the next candidate on any command failure, instead of under-delivering on the target count whenever the first few candidates happen to include a deposit charge.
37. **Nexudus's generic 500 (`"Ooops! There was a problem while running this action..."`) is not always deterministic — it can be plain transient flakiness, and it can come in bursts** — confirmed live: an identical `CrmOpportunity` create body (same coworker, same board column, same every field) failed twice, then succeeded 3/3 on immediate retry; retested later the same body failed 5 times in a row, then succeeded 8 times in a row right after, with no code or data change at any point. This is the exact same message text used for the genuinely deterministic rejections in rules 33/34 (both fixed at the data level) — the text alone doesn't tell you which kind you're looking at, and an initial 3-attempt retry wasn't always enough to ride out a bad streak. `nexudus_client.py::_request()` now retries a 500 carrying this message up to `MAX_TRANSIENT_ERROR_RETRIES = 6` times with increasing backoff (1.5s, 3s, 4.5s, ...), the same way it already retries 429s. `07_crm_proposals.py::_create_opportunities` also now catches any create failure that survives all those retries and skips that one record (opportunity history and proposals already had the `is None` guard needed to skip cleanly downstream) rather than crashing the layer.
38. **`teardown.py` had two ordering/coverage gaps found by comparing a real teardown run's before/after tracked counts**: (a) `coworkertimepasses` was deleted *before* `checkins` — a `CheckIn` can reference a `CoworkerTimePass` via `CoworkerTimePassGuid` (see rule 33 / `_grant_day_pass`), and a real run showed exactly the signature of this blocking: only 41 of 138 tracked passes succeeded when checkins hadn't been cleared yet. Fixed by moving `checkins` before `coworkertimepasses`. (b) `coworkerinvoices` was never actually deletable *or* trackable — `COWORKER_BILL_RUN` returns nothing usable (confirmed live: bare `None`), so no invoice ID was ever recorded anywhere except the small subset later voided/credited/refunded; `06_financial.py::_list_invoices` now tracks every invoice it discovers under `DiscoveredInvoiceId`, but only for a coworker this tool created (cross-checked against `coworker_ids`, never by bare business-scope — a shared business could have real invoices from real coworkers mixed in). Skipped entirely in dry-run.
39. **`coworkers`, `coworkerinvoices`, and `coworkercontracts` all reject a plain DELETE outright (405/no support) — all three actually delete via a command instead**, found by capturing the real admin UI's network requests (same technique as rule 27): `COWORKER_DELETE`, `COWORKER_INVOICE_DELETE`, and — for contracts specifically — a two-step `CANCEL_CONTRACT` then `DELETE_CONTRACT` sequence (a contract must be cancelled before it can be deleted; both commands confirmed live). `teardown.py`'s `COMMAND_DELETE` map now special-cases all three — every other entity in `ENTITY_DELETE_ORDER` still uses a plain `nexudus_delete`. For the two-step case, `_delete_one()` tolerates an earlier step failing (e.g. `CANCEL_CONTRACT` on a contract already cancelled by a prior partial teardown) as long as the *last* step in the sequence succeeds — only the final command's failure is actually surfaced.
40. **A `DELETE` returning 404 means the record is already gone, not that deletion failed** — confirmed live via a systematic one-record-per-entity teardown probe: several entities (`bookingvisitors`, `communitymessages`, `coworkerledgerentries`, `coworkertimepasses`, `floorplandesks`) had stale tracked IDs pointing at records that no longer existed (likely cascade-deleted or removed by an earlier partial teardown). `teardown.py` previously treated this identically to a real failure, leaving the stale ID in the tracking file forever, re-reported as "failed" on every future run. Now a 404 is treated as the desired end state — logged distinctly and cleared from tracking like any other successful delete.
41. **`04_activity.py::_create_extra_services`'s booking-charge path tracked a fake, non-deletable Id** — `CHARGE_BOOKING`'s response doesn't carry the new `CoworkerExtraService`'s own Id (just a bare success envelope), so this synthesized a `"charge-booking-{bookingId}"` string purely so `already_created()` had something to match on. That's fine for idempotency but not a real Nexudus Id — confirmed live `teardown.py` gets a 404 trying to delete it (now handled gracefully per rule 40, but the real record it should have deleted is never touched — an orphan left behind). Fixed to look up the real Id via `nexudus_list("coworkerextraservices", {"CoworkerExtraService_BookingId": booking_id})` right after charging. ~40 pre-existing tracked entries from before this fix still carry the fake Id; not backfilled (would cost 40 more live calls for a one-time historical artifact) — they'll simply 404-and-clear per rule 40 on the next teardown, leaving their real underlying records as one-time orphans.
