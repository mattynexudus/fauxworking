# Fauxworking — Agent Instructions

## What this repo does

Generates and seeds realistic test data into a Nexudus instance via MCP tools.
The data populates all reports and dashboards defined in the reports repo.

## Key commands

- `python generators/00_reference.py` — Tax rates, financial accounts, resource types
- `python generators/01_structural.py` — Tariffs, products, resources, desks, inventory, discounts, CRM boards
- `python generators/02_people.py` — Coworkers (with engagement fields) and visitors
- `python generators/03_contracts.py` — Contracts (with ContractTerm), deposits, freezes, occupancy
- `python generators/04_activity.py` — Bookings (recurring + products + guests), check-ins, credits, passes
- `python generators/05_community.py` — Deliveries, events, help desk, threads, blogs, tasks
- `python generators/06_financial.py` — Trigger invoices, pay/void/credit, ledger supplements
- `python generators/07_crm_proposals.py` — Opportunities, proposals (accept some → auto contracts)
- `python generators/daily_update.py` — Create today's check-ins, bookings, visitors, deliveries
- `python refresh_output.py` — Re-sync output/ with what Nexudus generated on its own (currently just coworkerinvoices — see rule 49) since the last run, and re-export every entity's CSV, including the live-only `coworkerinvoicelines.csv`
- `python teardown.py` — Delete every tracked record (agent-run; see rule 6)
- `bash scripts/seed_all.sh` — Run all generators in order
- `bash scripts/daily.sh` — Run daily update (fresh records for today)
- `bash scripts/verify.sh` — Count tracked records against config.py targets
- `bash scripts/teardown.sh` — Confirmation prompt, then runs `teardown.py` live for real (see `teardown.py` for `--dry-run`)

## Standing rules

1. **All dates are rolling** — derived from `config.TODAY`. Never hardcode dates.
2. **Check idempotency** — before creating, query for existing records with same key.
3. **Respect dependency order** — never create a child before its parent.
4. **Use config.py** for all magic numbers (volumes, dates, business IDs).
5. **Dates must be UTC with Z suffix** — use `config.to_utc_str()`.
6. **Never delete production data** — teardown only deletes IDs logged in `data/created-ids/<entity>.json`, never by name pattern. Note: entities only mutable via commands (e.g. `coworkerinvoices` void/credit-note records — see rule 12) have no plain delete path other than `COWORKER_INVOICE_DELETE`, which `teardown.py` does not currently special-case; it may error or no-op on these tracked entries. Not yet exercised live.
7. **No `[TEST]` name prefixes** — records should look like real data (reports/dashboards are demoed off this). `TEST_NAME_PREFIX` in `config.py` is `""`. The only marker baked into a record is the coworker email (`test-{id}@seeddata.local`); everything else is identified purely by its tracked ID.
8. **No "whoami" MCP tool** — resolve business/currency/country/timezone via `nexudus_list("businesses", {})`, and the admin user (for `IssuedById`/`ResponsibleId`) via `nexudus_list("users", {})` filtered to `IsAdmin=true`. A login can have access to more than one business — `pipeline._select_business()` never silently picks one; it auto-selects only when there's exactly one, otherwise requires an explicit `business_id` (via `--business-id` on any generator/`pipeline.py`, or `wizard.py`'s interactive prompt) and fails loudly listing the options if that's missing or wrong.
9. **Log all created IDs** — append to `data/created-ids/<generator>.json` (one file per generator, not per Nexudus entity — each record is tagged with an `"entity"` field; see `teardown.py`).
10. **One MCP call at a time** — do not parallelise Nexudus calls.
11. **Cancelled bookings** — create the booking, then cancel it via `nexudus_run_command("bookings", "CANCEL_BOOKING", [id], parameters=[{"Name": "Cancellation Reason", "Value": <eBookingCancellationReason>}, {"Name": "Cancel without applying cancellation fee rules", "Value": true}])`. Confirmed live: a raw delete leaves `CancellationReason` at 0/Unknown. Reason enum values in use: NoLongerNeeded=1, TooExpensive=2, RebookedForADifferentTime=4, FailedToPayUpfront=5, NotCheckedIn=8 (see `CANCELLATION_REASON_MAP` in `generators/04_activity.py`).
12. **Invoices** — cannot be created directly; raise via `nexudus_run_command("coworkers", "COWORKER_BILL_RUN", [coworkerId, ...])`, which bills that coworker's active contract(s) plus any pending item sales (see rule 26). `coworkerinvoices` *does* support commands — confirmed live, despite not appearing under command discovery (see rule 27):
    - `VOID_INVOICE` (no parameters) — sets `Void=true` on the same record.
    - `COWORKER_INVOICE_CANCEL` (parameters: an `"Amount{invoiceId}"`-named field — the invoice ID is baked into the parameter *name*, not a separate value — plus `Preview` and `DoNotApplyCreditAutomatically`) — creates a *new*, separate negative-amount invoice with `CreditNote=true`, linked back via `OriginalInvoiceGuid`. This is credit-noting, not voiding.
    - `COWORKER_INVOICE_DELETE` — genuinely deletes the invoice (404 on follow-up GET). Not equivalent to void — it erases the audit trail. Don't use it for void/credit-note scenarios.
    - `COWORKER_INVOICE_REFUND` (parameters: `Amount{invoiceId}`, `Preview`, `ePaymentProvider0`) — only valid on an already-paid invoice. Unlike credit-note, flips `Refunded=true` + `RefundedOn` on the *same* record rather than creating a new one — confirmed live. `RefundedAmount` stays `0` despite existing on the schema, also confirmed live, unexplained. The `nexudus_run_command` MCP tool itself refuses this entity ("does not support run-command") even though the real API accepts it fine — verified working through this project's own direct REST client instead; this is the same false-negative pattern as command discovery (rule 27), just enforced client-side this time.
    Booking charges use `nexudus_run_command("bookings", "CHARGE_BOOKING", [bookingId])`, which sets `Booking.Invoiced=true` and creates the linked charge — not a standalone `CoworkerExtraService` with a manually-set `BookingId`.
13. **Proposals** — create at status=1 (Draft). Accepting requires commands, not a direct field update: `nexudus_run_command("proposals", "PROPOSAL_SEND", [id])` then `nexudus_run_command("proposals", "PROPOSAL_ACCEPT", [id])`. Confirmed live: a direct `ProposalStatus` update to 3 fails with "Accepted proposals cannot be changed," even on a brand-new Draft. Neither command appears under command discovery (see rule 27).
14. **Financial accounts** — assign to Products, ExtraServices, and Tariffs at creation time.
15. **Tax rates** — assign to Products, ExtraServices, and Tariffs at creation time.
16. **Discount codes** — apply via Proposal.DiscountCodeId or Booking.DiscountCode text field.
17. **Recurring bookings** — `Repeats` is schema-required even for one-offs (send `1`/Daily with `RepeatEvent=false`); set `RepeatEvent=true` + `RepeatEvery` + `RepeatUntil` for real series. `CalendarEvent` uses a different, more granular enum (`eCalendarEventRepeatCycle`) than `Booking`'s — don't assume they match.
18. **Booking products** — `BookingProducts` is a genuine inline child on `Booking.create` (`[{ProductId, Quantity}]`) — no separate call needed.
19. **Booking guests** — create `BookingVisitor` standalone with a real `VisitorId`, not via Booking's inline `BookingVisitors` (that path writes `VisitorFullName`/`VisitorEmail`, which are read-only on the standalone entity — ambiguous whether/how it resolves a Visitor).
20. **Daily update** — run `daily_update.py` for fresh daily records. Unlike the layer generators, it resolves its own context live (no `prev_output` chain) since it's meant to run standalone, repeatedly, long after the one-time seed.
21. **Events** — `CalendarEvent` has no inline children. Create order is `CalendarEvent` → `EventProduct` (a ticket type is **required** before any attendee, not optional) → `EventAttendee`. `OnlyForMembers` events reject `EventAttendee` creation for a coworker whose membership isn't *currently* active — contract cancelled, or in a currently-paused freeze (`CoworkerContract.InPausedPeriod`) — with `"You cannot purchase this product"`, confirmed live. This is enforced against the coworker's actual contract state, not the `Coworker.CanPurchaseEvents` flag (which stays `true` regardless). When generating attendees for such events, only pick from coworkers with a currently-active, unfrozen contract.
22. **Deliveries** — create as pending, then update `Collected=true` + `CollectedOn` (or `Forwarded`/`Recycled`/`ReturnedToSender` + their `*On` field) to mark an outcome.
23. **Community threads/messages** — require `UserId`, a field distinct from `CoworkerId`. Seeded coworkers have no linked User account (`Coworker.UserId` is `updateOnly`, not populated by creation), so the resolved admin user's ID is used as `UserId` throughout, with `CoworkerId` set alongside for attribution.
24. **Engagement fields** — `ChurnProbability`/`EngagementLevel` on `Coworker` are confirmed live: visible on GET, round-trip correctly.
25. **ContractTerm** — set on ~30% of contracts. This is the minimum term end date (start + N months), not a duration field.
26. **Item-sale invoicing** — `Booking`, `CoworkerExtraService`, and `CoworkerProduct` all support `InvoiceThisCoworker` (bill this person, not their team's payer). Set it `True` on all of them so their charges get swept into that coworker's next invoice by `COWORKER_BILL_RUN`, alongside their plan fee — this is the "item sales" invoicing path referenced in the original design, distinct from contract renewal itself.
27. **Command discovery is unreliable** — `nexudus_list_commands` and `GET .../commands?id=X` have both produced false negatives, confirmed live: missing `VOID_INVOICE` for `coworkerinvoices`, missing all of `proposals`' commands. If an entity's obvious field-update path fails with a vague error (e.g. "cannot be changed"), don't conclude the action is unsupported — check whether the entity has a `runcommand` endpoint, and if discovery doesn't surface what's needed, capture the real admin UI's network request instead. The `nexudus_run_command` MCP tool itself can carry the same false negative one step further and outright refuse a call ("does not support run-command") for an entity/command the real API accepts — confirmed live for `coworkerinvoices`/`COWORKER_INVOICE_REFUND`. When that happens, the generators' own direct REST client (not this MCP tool) is the one to trust — it's what actually runs live (see `nexudus_client.py`).
28. **Coworker has no `BusinessId` field** — it's two separate fields instead: `Businesses` (plural, a list — which businesses this coworker is linked to) and `InvoicingBusinessId` (their actual "home" business). Confirmed live: omitting both doesn't error, it silently falls back to some other business tied to the login/token; confirmed separately that updating `Businesses` alone does **not** move `InvoicingBusinessId` — both must be set explicitly. This only surfaces as a bug on a login with access to more than one business (see rule 8) — with a single-business account there's nothing for it to silently fall back to *other than* the right one, so this went unnoticed until tested against a multi-business login.
29. **Any `X_id = some_dict.get(...)` lookup on a possibly-skipped parent record needs an explicit `is None` guard before use** — a missing guard doesn't fail cleanly, it sends `null` for that field and the API rejects it with a misleading message (e.g. `BookingVisitor` with a skipped `Booking` fails as `"Booking: is a required field"`, not `"BookingId: null"`). This pattern is used correctly almost everywhere in the generators (see the many `if x_id is None: continue` guards) — `04_activity.py::_create_booking_guests` and `06_financial.py::_create_ledger_supplements` were the two places it was missing, both fixed. Audit new `.get()`-based parent lookups the same way, especially anything downstream of `Coworker` (the one record type most likely to be skipped, via the seat-limit `Exception` path in `02_people.py`).
30. **There's a ~50 coworker-creation limit per day, per the Nexudus API** (per-account, not per-business) — user-reported, not independently re-derived, but it matches the `"Access Denied"` behavior `02_people.py`'s existing seat-limit handling was already written defensively against. It resets some time later (exact window unconfirmed) — if a live run stops partway through coworkers with `"Access Denied"`, that's very likely this, not a bug, and every later layer's shortfall (bookings, contracts, etc. tied to the missing coworkers) cascades from the same root cause. Retrying immediately won't help; retrying tomorrow should.
31. **`nexudus_delete()` must check the response body, not just HTTP status** — confirmed live: a DELETE can return HTTP 200 (so `resp.ok` is `True`) with `WasSuccessful: false` in the body for a genuinely failed delete (e.g. a `BookingVisitor` its sibling record blocks from being deleted). `nexudus_client.py::nexudus_delete()` only checked `resp.ok` for a long time, which silently reported these as successes — the same class of bug `_unwrap()` already guards against for create/update/run_command, just missed on delete. Now fixed to check `WasSuccessful` the same way. If a delete-based fix ever looks like it "succeeded" but the record is still there on the next GET, suspect this pattern, not a timing issue.
32. **A `Visitor` who is a guest on more than one `Booking` can leave a `BookingVisitor` link permanently stuck — and this is common here, not rare.** Confirmed live: cancelling a booking normally cascades-deletes its `BookingVisitor`(s) fine via `CANCEL_BOOKING`, and even a direct isolated `DELETE` on a normal `BookingVisitor` works. But when the same `Visitor` is attached to two different bookings, one of those two links can become permanently undeletable — every direct `DELETE` attempt on it fails identically and reproducibly with `"You must delete all booking visitors using this record before you can delete it."`, even in total isolation (not a timing/order artifact). The fix is not to pre-delete guests before cancelling (that doesn't work and isn't needed for the normal case) — `04_activity.py::_cancel_bookings` catches this specific error message and skips that one booking's cancellation with a warning, rather than crashing the whole run. Originally found via two specific stuck records and described as a rare edge case — a live teardown run later showed dozens of consecutive `bookingvisitors` deletes failing the same way. With only ~56 tracked visitors reused as guests across 126+ bookings, most visitors end up on more than one booking, so this isn't rare here, it's the norm — see rule 40 for how teardown handles it.
33. **An "open" `CheckIn` (no `ToTime` — still checked in) must be dated today** — confirmed live: a `CheckIn` with `Open=true` and `FromTime` on any day other than today fails with a generic, unhelpful 400 (`"Ooops! There was a problem while running this action..."`), not a field-specific message. Traced to a specific failing record (`FromDayOffset=-1`) to confirm. `prebuild.py::generate_checkins()` now forces `FromDayOffset=0` for the handful of check-ins it marks `Open`, rather than sampling from a "within the last few days" pool. `04_activity.py::_create_checkins` also now catches any create failure (not just the already-handled "no valid time pass" case) and skips that one record with a warning instead of raising — a bad check-in shouldn't take down the rest of the layer (extra services, credits, time passes, coworker products all run after it).
34. **`EventAttendee` effectively requires a real `CoworkerId`, despite the docs listing it as optional** — confirmed live via isolated testing: an ad-hoc "guest" attendee (just `FullName`/`Email`, no `CoworkerId` — the documented flow for non-member walk-ins) fails with a generic 500 (`"Ooops! There was a problem while running this action..."`), on every event tested, with `CheckedIn` either `true` or `false`, and even when a real `VisitorId` is substituted in instead of a guest name/email. Only ever succeeds with a real `CoworkerId` attached. Same "docs unreliable" pattern as rule 27, just for a field instead of a command this time. `prebuild.py::generate_event_attendees()` no longer generates ad-hoc guest attendees at all — every attendee now gets a real `CoworkerIndex` (still respecting rule 21's active-members-only restriction for `OnlyForMembers` events). `05_community.py::_create_event_attendees` also now catches any create failure and skips that one record with a warning instead of raising.
35. **`COWORKER_BILL_RUN` over a large batch is slow enough to risk a timeout or the generic 400** — confirmed live: a single call billing 42 coworkers at once took 28.8s (once genuinely exceeded the client's 30s timeout), right at the edge of producing an unhelpful failure with no way to tell which coworker (if any) was actually the problem. Testing each of the 42 coworkers individually (including several with a currently-frozen contract, to rule out rule 21's "frozen membership" pattern applying here too) all succeeded fine on their own — it's genuinely a batch-size/latency issue, not a bad record. `06_financial.py::_raise_invoices` now calls `COWORKER_BILL_RUN` in chunks of `BILL_RUN_CHUNK_SIZE = 10`, and a failed chunk is logged and skipped rather than aborting billing for every other coworker.
36. **`COWORKER_INVOICE_REFUND` rejects an invoice that includes a Deposit line** — confirmed live: `"You cannot refund X for line Deposit (#id)"`. `ContractDeposit` has its own refund path (`Refundable` + `Credited`, triggered by cancelling the parent contract), not a generic invoice refund — and `InvoiceLines` isn't populated on either the list or single-GET `coworkerinvoices` response, so there's no cheap way to detect this up front and exclude such invoices from the refund pool. `06_financial.py::_refund_invoices` now takes the full refund-candidate pool (not pre-sliced to `REFUND_COUNT`) and falls through to the next candidate on any command failure, instead of under-delivering on the target count whenever the first few candidates happen to include a deposit charge.
37. **Nexudus's generic 500 (`"Ooops! There was a problem while running this action..."`) is not always deterministic — it can be plain transient flakiness, and it can come in bursts** — confirmed live: an identical `CrmOpportunity` create body (same coworker, same board column, same every field) failed twice, then succeeded 3/3 on immediate retry; retested later the same body failed 5 times in a row, then succeeded 8 times in a row right after, with no code or data change at any point. This is the exact same message text used for the genuinely deterministic rejections in rules 33/34 (both fixed at the data level) — the text alone doesn't tell you which kind you're looking at, and an initial 3-attempt retry wasn't always enough to ride out a bad streak. `nexudus_client.py::_request()` now retries a 500 carrying this message up to `MAX_TRANSIENT_ERROR_RETRIES = 6` times with increasing backoff (1.5s, 3s, 4.5s, ...), the same way it already retries 429s. `07_crm_proposals.py::_create_opportunities` also now catches any create failure that survives all those retries and skips that one record (opportunity history and proposals already had the `is None` guard needed to skip cleanly downstream) rather than crashing the layer.
38. **`teardown.py` had two ordering/coverage gaps found by comparing a real teardown run's before/after tracked counts**: (a) `coworkertimepasses` was deleted *before* `checkins` — a `CheckIn` can reference a `CoworkerTimePass` via `CoworkerTimePassGuid` (see rule 33 / `_grant_day_pass`), and a real run showed exactly the signature of this blocking: only 41 of 138 tracked passes succeeded when checkins hadn't been cleared yet. Fixed by moving `checkins` before `coworkertimepasses`. (b) `coworkerinvoices` was never actually deletable *or* trackable — `COWORKER_BILL_RUN` returns nothing usable (confirmed live: bare `None`), so no invoice ID was ever recorded anywhere except the small subset later voided/credited/refunded; `06_financial.py::_list_invoices` now tracks every invoice it discovers under `DiscoveredInvoiceId`, but only for a coworker this tool created (cross-checked against `coworker_ids`, never by bare business-scope — a shared business could have real invoices from real coworkers mixed in). Skipped entirely in dry-run.
39. **`coworkers`, `coworkerinvoices`, and `coworkercontracts` all reject a plain DELETE outright (405/no support) — all three actually delete via a command instead**, found by capturing the real admin UI's network requests (same technique as rule 27): `COWORKER_DELETE`, `COWORKER_INVOICE_DELETE`, and — for contracts specifically — a two-step `CANCEL_CONTRACT` then `DELETE_CONTRACT` sequence (a contract must be cancelled before it can be deleted; both commands confirmed live). `teardown.py`'s `COMMAND_DELETE` map now special-cases all three — every other entity in `ENTITY_DELETE_ORDER` still uses a plain `nexudus_delete`. For the two-step case, `_delete_one()` tolerates an earlier step failing (e.g. `CANCEL_CONTRACT` on a contract already cancelled by a prior partial teardown) as long as the *last* step in the sequence succeeds — only the final command's failure is actually surfaced.
40. **A `DELETE` returning 404 means the record is already gone, not that deletion failed** — confirmed live via a systematic one-record-per-entity teardown probe: several entities (`bookingvisitors`, `communitymessages`, `coworkerledgerentries`, `coworkertimepasses`, `floorplandesks`) had stale tracked IDs pointing at records that no longer existed (likely cascade-deleted or removed by an earlier partial teardown). `teardown.py` previously treated this identically to a real failure, leaving the stale ID in the tracking file forever, re-reported as "failed" on every future run. Now a 404 is treated as the desired end state — logged distinctly and cleared from tracking like any other successful delete.
41. **`04_activity.py::_create_extra_services`'s booking-charge path tracked a fake, non-deletable Id** — `CHARGE_BOOKING`'s response doesn't carry the new `CoworkerExtraService`'s own Id (just a bare success envelope), so this synthesized a `"charge-booking-{bookingId}"` string purely so `already_created()` had something to match on. That's fine for idempotency but not a real Nexudus Id — confirmed live `teardown.py` gets a 404 trying to delete it. Fixed to look up the real Id via `nexudus_list("coworkerextraservices", {"CoworkerExtraService_BookingId": booking_id})` right after charging. ~40 pre-existing tracked entries from before this fix still carry the fake Id and were left un-backfilled at the time — **that assessment was wrong, see rule 43**: the orphan this leaves behind isn't harmless, it actively blocks its booking from being deleted.
42. **`bookings` also rejects a plain DELETE with "You must delete all booking visitors..." — and per rule 32, that's the norm here, not an edge case.** A live teardown run showed dozens of consecutive `bookingvisitors` delete failures in a row for exactly this reason. Since `CANCEL_BOOKING` already cascades-removes a booking's guests correctly (rule 32), `teardown.py`'s `bookings` entry now runs `CANCEL_BOOKING` (with the same parameters used at seed time — Cancellation Reason=Other, no fee rules applied) before the plain `DELETE`, tolerating an "already cancelled" failure on the ~25 seeded pre-cancelled bookings the same way the `coworkercontracts` sequence tolerates an already-cancelled contract.
43. **A booking that's already been charged rejects DELETE even after cancelling** — `"This booking has already been charged to this customer."`, confirmed live. This is rule 41's fake-Id bug coming back around: the ~40 pre-existing booking-charge records tracked under a fake `"charge-booking-X"` Id 404'd (correctly treated as already-gone per rule 40) without ever deleting the *real* charge record, which is still attached to its booking and blocks it. `teardown.py::_delete_one` now self-heals for `bookings` specifically: on this exact error, it looks up the real charge live via `nexudus_list("coworkerextraservices", {"CoworkerExtraService_BookingId": booking_id})`, deletes what it finds, and retries the cancel+delete sequence once. Also fixed while addressing this: a credit note (`COWORKER_INVOICE_CANCEL`'s output, rule 12) is a separate `CoworkerInvoice` linked back to the one it credited via `OriginalInvoiceId` — a real child-before-parent dependency *within* the `coworkerinvoices` batch that nothing previously ordered for. `run_teardown` now sorts credit notes (tracked with `OriginalInvoiceId`) to the front of that batch, per the user's direct guidance that clearing invoices (credit notes before their originals) early is what unblocks most of the "sales item" entities (bookings, coworkerproducts, coworkerextraservices) downstream.
44. **Local-tracking-only idempotency can silently drift from live reality across repeated reseed cycles, leaving untracked duplicates that block `COWORKER_DELETE` with no diagnostic text** — confirmed live: the exact same coworker had both an untracked, *paid* `CoworkerInvoice` and 32 untracked `CoworkerProduct` records (all matching this project's own tracked Product Ids), both created in the same ~16:45 batch — almost certainly a reseed that ran between two teardown attempts, recreating records `already_created()` had no memory of because a prior successful teardown had already cleared the local tracking for what came before. Confirmed by direct elimination against ~15 other candidate entity types (contracts, proposals, opportunities, bookings, visitors-as-host, floorplandesks, team paying-member, etc. — all clean) before finding these two, and confirmed as the actual cause by deleting them live and watching `COWORKER_DELETE` succeed immediately after. Unlike rule 43's `bookings` case, `COWORKER_DELETE`'s failure is always the same generic 500 with no distinguishing text to key off of, so `teardown.py::_delete_one` checks these two known accumulation points proactively for `coworkers` rather than reacting to a message — see `_COWORKER_CLEANUP_TARGETS`. This is a narrower, project-level instance of a broader risk worth remembering: any per-record local-tracking idempotency check (`already_created()`) is only as good as the tracking file's own continuity — a teardown that clears tracking without also fully succeeding live, followed by a reseed, can silently recreate what looks like fresh data but is actually an undetected duplicate.
45. **A full teardown of this account eventually succeeded down to the two genuinely undeletable entities** (`cancelledbookings`, `coworkerbookingcreditusehistories` — no delete endpoint at all, see the module docstring). One last blocker along the way: `financialaccounts`/`taxrates` deletion failed with `"You must delete all event products using this record before you can delete it"` even though `eventproducts` showed zero tracked locally — 45 live `EventProduct` records (all `"General Admission"`, clustered at the original seed's timestamp) had never been tracked at all, a historical gap predating this session's tracking fixes, not an active recurring drift like rule 44. Confirmed genuinely ours (name pattern + timestamp cluster) and cleaned up directly rather than adding new self-heal code for what looks like a one-off artifact.
46. **This account has substantial pre-existing content unrelated to this tool — a "clean" teardown will never show zero live records overall, only zero tracked ones.** After rule 45's teardown, the user reported "still invoices, contracts and events" visible live. Investigated each: 89 `coworkercontracts` and 193 `bookings` are 100% pre-existing (`CreatedOn` dates spanning 2022–mid-2026, none matching any seed date this project used) — untouched, correctly, since teardown only ever deletes by tracked ID (rule 6/7). A recurring real customer, "Chift Integration"/"Philip Banks" (`CoworkerId` 1123713612 — well outside this project's `142360xxxx` test-coworker range), has genuine automated billing firing every ~6 hours, which is why some of its invoices/products coincidentally fell inside this session's testing window and looked suspicious by date alone before checking `CoworkerId`. The one thing from this check that *was* genuinely ours: 45 live `CalendarEvent` records (same date-clustered, name-matching pattern as rule 45's `EventProduct`s — `"Weekly Networking Lunch"`, `"Yoga Wednesday"`, etc.), never tracked, found and deleted. Lesson: when auditing "is this ours," a `CreatedOn` date near a seed run is suggestive but not sufficient — cross-check `CoworkerId` against the actual tracked/known ID range (or the record's own distinguishing content) before deleting anything not found via a tracked ID.
47. **`TariffTimePass`/`TariffExtraService` (join tables linking Tariff↔TimePass and Tariff↔ExtraService) block deletion of `timepasses`/`extraservices`/`resourcetypes`/`financialaccounts`/`taxrates` if left too late** — confirmed live: `"You must delete all price plan time passes..."` / `"...resource credits..."` / `"...ExtraServices_ResourceTypes..."` / `"...resource rates..."` on those five entities. Neither join table was in `ENTITY_DELETE_ORDER` at all, so they only ever got processed last (alphabetically, appended after every explicit entry) — too late to unblock anything. Moved both right after `resources`, before `timepasses`/`extraservices`/`tariffs`. Retrying the 10 records this had blocked in a real run confirmed 10/10 now succeed. Separately: `teardown.py` also gained an optional post-teardown feature (user-added) offering to reset a business's `Billing.Current{Booking,CreditNote,Draft,Invoice}Number` counters to 0 — deleting records doesn't roll these back. 48. **`teardown.py` had no isolation boundary above one record's delete call — anything that escaped that per-record layer took down the entire run, and a genuinely-partial seed (a foundational failure, an independent-tier layer failure, a manual interrupt, the rule 30 coworker limit) made hitting that layer more likely, not less.** Found by code audit and reproduced directly (not a live-account incident like the rules above): `by_entity.setdefault(item[2].get("entity"), []).append(item)` used a possibly-`None` key with no guard whenever a tracked record was missing its `"entity"` tag — the same "stray file in `data/created-ids/`" scenario `report_lib.py::_grouped_records()` already defends against on the reporting side. `sorted(set(by_entity) - set(ENTITY_DELETE_ORDER))` then raised `TypeError: '<' not supported between instances of 'NoneType' and 'str'` the instant a *second*, genuinely-unlisted entity name was also present that run (a one-element `{None}` set alone doesn't force a comparison) — killing the whole teardown before a single record was touched; without that second condition, the `None` entity instead reached `_delete_one(None, ...)` and got stuck permanently under a confusing, mislabeled failure. Fixed by skipping any pooled item missing/`None`-tagged `"entity"` (or not even a dict) with a warning, same pattern as `_grouped_records()`. Separately, each entity's whole batch (`_delete_entity_batch()`: the `coworkerinvoices` credit-note sort, the `NO_DELETE_SUPPORT` skip, the per-record loop) is now wrapped in its own try/except inside the main `for entity in ordered_entities:` loop — mirroring `pipeline.py`'s per-layer isolation (see `HARD_DEPENDENCY_LAYER_COUNT`) one level down, at entity-type granularity — so a failure there is logged distinctly from a per-record failure and the run moves on to the next entity instead of aborting entirely. The survivor-persistence rewrite and final summary now run from a `try/finally` around that loop, so nothing deleted this run is ever left stranded in tracking even if some entity's batch aborts partway. `run_teardown()` now returns a summary dict (`{seen, deleted, skipped_no_support, failed, malformed, entity_outcomes}`) instead of nothing, with `entity_outcomes` giving a per-entity Seen/Deleted/Failed breakdown plus failure-reason counts, rendered by `teardown_summary_lines()`. A small pre-flight check (`_last_generation_run_incomplete()`) prints a heads-up if `last-run-report.txt` shows the last generation run didn't fully complete — checked via `report_lib.py`'s own literal marker strings (`"Layers that failed entirely this run"`, `"<-- short"`) since teardown runs as a separate process with no access to `pipeline.py`'s in-memory `LAST_RUN_*` globals. Deliberately excludes `report_lines()`'s `"<-- below target"` flag from that check — that one is cumulative/lifetime and can be true for reasons unrelated to the last run's completeness (a raised volume config, a multi-day seeding plan not finished by design), which a first pass at this mistakenly included and a test written against the real project's own `last-run-report.txt` caught immediately.
49. **`output/*.csv` is a pure re-derivation of local tracking (`report_lib.write_entity_csvs`), so it silently drifts from live reality for exactly one entity: `coworkerinvoices`.** Nexudus raises invoices for a coworker's recurring contract on its own over time, independent of this project's `nexudus_raise_invoice` calls (see `06_financial.py::_select_invoices` — confirmed live the tracked pool grows run over run with no code change here). The entity's `apiPath`/module (`coworkerinvoicelines`, `billing`) came from the user directly, not independent discovery.
50. **`prebuild.py` is incremental by default now — the "run once, commit the JSON" note in its old docstring no longer holds.** A `data/plan-manifest.json` (`{seed, generated_at, counts}`) records the last run. Incremental mode kicks in whenever a plan is already on disk *and* the seed hasn't changed — it does **not** require a matching manifest (so a fresh clone with committed `data/*.json` and no manifest still adopts what's there rather than rebuilding it). It keeps every record already on disk in each `data/*.json` and appends only `records[len(existing):]` — bumping `--coworkers 50` to `60` adds 10, it never rewrites the first 50 (which may already be seeded live) and never shrinks a file (a lowered count just prints a "prebuild only grows — use teardown to remove" line). If **no** configurable target exceeds what's on disk (`_plan_covers()`), generation is skipped entirely — `generate_all` prints "Plan already covers every target — skipping regeneration" and returns after just refreshing the manifest. This is what lets the web control panel's guided flow ("Set up demo data" → `wizard`) be the single seeding path: it always calls `generate_all` then `pipeline.run_up_to`, but the regenerate half is a near-instant no-op unless you actually raised a volume / changed the seed / ticked "start fresh" — so there's no separate "just seed the current plan" card (the `pipeline` command stays in `webui/registry.py` as `hidden=True` for CLI/API parity). `--fresh`, or any change to `--seed`, forces the old wholesale regenerate. The splice keys off each file's actual length, not the manifest — the manifest's `counts` are just a cache for the control panel's `GET /api/plan` readout. `generate_all(seed, volumes, fresh=False)` gained the flag; `wizard.py` and the browser guided flow thread it through (`--fresh` / the "Start data fresh" checkbox). `teardown.py::maybe_clear_generated_data()` already globs `data/*.json`, so it clears `plan-manifest.json` too when you accept that prompt — correct, since the (now deleted) records shouldn't look "already generated" to the next prebuild. The reason the low-index records genuinely drift on a non-incremental re-run: `generate_coworkers` calls `rescale_plan(LIFECYCLE_SCENARIOS, count)`, so the scenario bucket sizes (and therefore per-index scenario, churn, attendance, and all downstream RNG draws) change with `count` — only identical inputs give identical output. The live seed was already incremental regardless (every generator checks a positional `*Index`/`Email` key against `data/created-ids/*.json` and skips what's tracked); this change just stops the *plan* files from silently disagreeing with what those checks already protect.
51. **Invoice dates are *constructed*, not shifted — and the due-date offset comes from the account's own business setting.** `06_financial.py::_backdate_invoices` used to move every populated date field on an invoice by one random negative delta, which preserved the record's internal structure but never fixed it: Nexudus bills whatever period a contract is next due for, so a live invoice came back `CreatedOn 2026-08-27`, `DueDate 2026-08-30`, `InvoiceFromDate 2025-03-31` — a billing period 17 months adrift from its own invoice date — and a uniform shift carried that adrift-ness along unchanged. Replaced by `_schedule_invoice_dates`, which builds each invoice a real schedule: issued in the last five days of some month inside the 24-month window, due `_default_due_days` later, for a period starting on the 1st of the month that *follows* (billed in advance). The period's *length* is still taken from what Nexudus produced (`_period_length`), so a Flex Weekly invoice stays a 7-day period and a quarterly one stays 3 months, with lengths inside 27–32 / 85–95 / 175–190 / 360–372 days snapped to exactly 1 / 3 / 6 / 12 months so monthly plans land on clean boundaries. `_default_due_days` reads the offset from `businesssettings` (the key the user named is `tariffDefaultDueDate`, normally 3) — matched case-insensitively against the last dotted segment of each setting `Name`, since the prefix convention varies (`Billing.CurrentInvoiceNumber` in rule 47 vs. a bare key here), falling back to `config.DEFAULT_INVOICE_DUE_DAYS = 3`. Same client-side filtering as rule 47: that endpoint ignores every filter param. **Not yet verified live** — this session had no `.env`/token, so the exact setting key and its presence on this account are still unconfirmed; the lookup is written to tolerate not finding it.
52. **A payment (`CoworkerLedgerEntry`) sent no date at all, so every payment this tool ever made landed at seed time.** The entry has a `TransactionDate` (visible on every tracked record) that was never populated on create, leaving the server to stamp "now" — which made aging, days-to-pay and cash-flow reporting meaningless no matter how well the invoices themselves were dated. `_pay_invoices` now takes the schedule map `_schedule_invoice_dates` returns and draws a payment date around that invoice's *own* due date via `PAYMENT_TIMING_BUCKETS` (mostly on time, thinning tail of late payers), clamped to never precede the invoice or land in the future. Creating the ledger entry also stamps the invoice's read-only `PaidOn` with "now", so that's corrected immediately afterwards — and since `nexudus_update` is a read-modify-write, the correction resends `CreatedOn`/`DueDate` alongside so a full-record PUT can't quietly undo the schedule. Same treatment for the two other actions that used to strand a record at seed time: a credit note (a *new* invoice, rule 12) is re-dated to a few days after the invoice it credits, and `RefundedOn` to a few days after the payment it reverses. Whether `CoworkerLedgerEntry` accepts an explicit `CreatedOn` on create is unconfirmed, so the first payment of a run includes it and falls back to retrying without it on failure, remembering the answer for the rest of the run (`_ledger_created_on_writable`).
53. **Floor plan unit occupancy belongs on the contract, not the coworker.** (Which field carries the link is now settled — see rule 55, which supersedes the shape-probing described here.) `03_contracts.py::_assign_desks` used to write `{"CoworkerId": ..., "Available": False}`, which models occupancy on the wrong record: what occupies an office is the office *contract*, and the unit type has to match the plan type (office unit ↔ office plan, hot desk ↔ hot desk/flex). `prebuild.py::generate_desk_assignments` already paired them that way and threw the contract away; it now emits `ContractIndex` too, and the plan-name buckets both sides need live in `config.DESK_PLAN_TYPES` / `DESK_ITEM_TYPE_PLAN_BUCKET` so prebuild and the generator can't drift. 57. **`CrmOpportunity.Position` is an insertion index, not a display weight — send it and a fresh column rejects every create with the generic 500.** This is what made all 30 opportunities fail in the 2026-09-02 run (and, cascading from it, all 90 opportunity-history records). Bisected live against an otherwise-identical body, one field at a time: omitting `Position` succeeds on both an empty and a populated column; `Position: 1` **fails on an empty column** but succeeds once the column has items (stored as 100); `Position: 100`/`200` fail. So the value has to fall inside the range of what's already in the target column, and Nexudus then resequences everything to spaced multiples of 100 (1, 100, 200, 300) — which is why the earlier read of this ("auto-normalizes to multiples of 100, so always send 1") looked right at the time: it was tested against a board that already had opportunities in it. Post-teardown, or on any first seed, the Lead column is empty and `1` is out of range. `07_crm_proposals.py::_create_opportunities` no longer sends the field at all, which lets Nexudus append; `prebuild.py` still emits `Position` in the plan for file compatibility but nothing reads it. Two general lessons: (a) a field whose stored value never matches what you sent is a hint that the server is *interpreting* it, not storing it — don't assume "ignored"; (b) rule 37's transient-500 retry (6 attempts) plus `classify_failure`'s systemic stop made this look exactly like the bursty flakiness of rule 37 in the log — 14 records failing identically, then a "stopping, this error has repeated" line — so a run-long streak of one entity failing while other entities succeed around it should be bisected as a real rejection, not written off as flakiness.
